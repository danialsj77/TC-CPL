# TC-CPL — Transformer-Constrained Charging Policy Learning

Code and experiments for the manuscript **"EV Charging Policy Learning for Power
Setpoint Tracking with Transformer Limit Constraint"** (D. Sajedi-Hosseini and
X. Shen, Tokyo University of Agriculture and Technology; for IEEE Transactions
on Transportation Electrification), built on the
[EV2Gym](https://github.com/StavrosOrf/EV2Gym) simulator.

The code implements the manuscript's Sec. III **exactly**: the grid-aware
observation with fixed physical feature scaling, residual anchoring at the
incumbent's action (ρ = 0.25, Eq. (projection)), the exact normalized costs
with the terminal service deficit, the PI dual controller in M1, prioritized
replay with importance weights (β annealed to 1), per-transformer pooled actor
and twin critics with a shared per-port residual head (M3), the dynamic entropy
target −|J_ctrl|, and finite-horizon γ = 1 returns.

## Layout

| Path | Role |
|---|---|
| `TC-CPL.ipynb` | The end-to-end pipeline: mechanisms (§5), training of all learners (§6), evaluation, statistics and every figure/table of the manuscript (§7–8). |
| `tccpl_learner.py` | **The TC-CPL learner stack** — observation, residual wrapper, costs, PI dual callback, demonstrations, prioritized buffer, structured actor/critics, `TCCPLSAC`. Run `python tccpl_learner.py` for a self-test (shapes, masking, permutation equivariance, gradients). |
| `cpo_pst.py` | Constrained Policy Optimization baseline (Achiam et al., 2017). |
| `export_training_module.py` | Regenerates `tccpl_runtime.py` from the notebook. **Re-run after editing notebook cells 4–47.** |
| `tccpl_runtime.py` | AUTO-GENERATED — notebook definitions + one `train_<algo>()` per job, importable outside Jupyter. Do not edit by hand. |
| `train_one.py` | One controller × one seed × one scenario as a standalone process: `python train_one.py --algo tccpl --seed 42 --scenario cityNL`. |
| `runall.sh` | **All five algorithms of one scenario at the same time** (one process each): `./runall.sh cityNL 42`. `SMOKE=1` rehearses everything in ~2 min; finished jobs are skipped on re-run. |
| `run_sweep.py` | Same jobs with *bounded* concurrency (default 2 at a time), all seeds × scenarios queued: use it when RAM is tight or you want the whole protocol unattended. |
| `ev2gym/` | The EV2Gym simulator package (environment, Dutch field data, heuristics, plotting). Kept intact. |
| `Related Papers/` | Literature by pillar; **Pillar 0** is the closest related work. |
| `models/<scenario>/`, `logs/<scenario>/`, `results/<scenario>/`, `cache/` | Created by runs — everything is namespaced by scenario so the two studies never collide. |

## What is in this repository

Everything needed to reproduce the study: the learner, the notebook, the launchers,
the EV2Gym fork with the two scenario configurations, the manuscript figures
(`figs/`) and the evaluation artefacts that back every number in the paper

## The two validation scenarios

When the notebook starts in Jupyter, its §2 cell **asks which scenario to run**:
it lists both configurations, prints the main characteristics of the one you
pick (read from the YAML and from what is already trained/evaluated on disk) and
waits for `yes` — any other answer offers the choice again. Headless launchers
(`train_one.py`, `runall.sh`, `run_sweep.py`) select it with the `TCCPL_SCENARIO`
environment variable instead and are never prompted (default `cityNL`):

- **`PublicPST`** — the single-transformer public facility of the PST paper:
  20 charge points behind one 100-kW transformer, 112 × 15-min steps, no grid
  simulation. Fast; good for smoke tests and the small-scale study.
- **`cityNL`** — the city-scale scenario: 122 MV/LV substations on a real
  feeder model, 300 dual-socket stations (600 ports), full AC power flow,
  96 × 15-min steps.

## Setup (any machine, including a cluster)

```bash
git clone https://github.com/danialsj77/TC-CPL.git && cd TC-CPL
python3.11 -m venv .venv && source .venv/bin/activate     # Python 3.10 or 3.11
pip install -r requirements.txt
python tccpl_learner.py                                   # self-test, ~10 s
SMOKE=1 ./runall.sh PublicPST                             # 2–15 min rehearsal of all five learners
```

The `SMOKE=1` rehearsal trains every learner for 300 steps and writes real
artefacts, but marks them as smoke runs so the completion checks never mistake
them for finished models. Delete `models/`, `logs/` and `results/` afterwards
before the real protocol. Torch picks CUDA when available (`TCCPL_DEVICE=cpu`
forces CPU).

## Workflow

1. **Train** — `python run_sweep.py` (all algorithms × 5 seeds × 2 scenarios as
   parallel processes, 1,000,000 environment steps each), `sbatch slurm_sweep.sh`
   on a SLURM cluster (one array task per job, see *Cluster protocol* below), or
   run notebook §6 top-to-bottom (the notebook asks for the scenario at start;
   set `TCCPL_SEED` for another seed). `TCCPL_TOTAL_TIMESTEPS` and `TCCPL_SEEDS`
   shrink the protocol for local runs (e.g. `300000` and `42`).
2. **Evaluate** — run notebook §7 once per scenario. It discovers every seed in
   `./models/<scenario>/` and aggregates (per-episode metrics averaged over
   seeds; learning curves and λ trajectories drawn as the mean with a min–max
   band across seeds, with the per-seed final multipliers and a convergence
   trend printed under the λ figure); all controllers are evaluated on the
   same 100 paired days.
3. **Export** — §7–8 write every table/figure into `results/<scenario>/`
   (PNG + CSV/JSON; figures are PNG only; §7.4 also records the overload beyond dead bands of 0.5–20 kW, 1–5 % of nameplate and the nameplate rating per day; both §7.9 figures report the 10-kW band, chosen because the violation probability of TC-CPL is near zero there while the baselines stay well above it). The manuscript's design-region
   figure (§7.9) is one row of four panels per scenario — (a) $|\epsilon_{tr}|$
   vs. overload, (b) vs. user satisfaction, (c) vs. delivered energy, (d) a
   compact legend — with every controller drawn and a bold red frame marking
   the magnified view of the desired region.

Controllers: TC-CPL (M1+M2+M3) · SAC (fixed λ) — **Algorithm 1 with the
multiplier update frozen**, everything else identical, so the pair isolates M1 ·
DDPG-PST and PPO-PST on the published `PublicPST` state · CPO on the grid-aware
observation with a flat MLP · CAFAP/ALAP/Round-Robin heuristics · the offline
convex-QP perfect-foresight benchmark.

## Device (Apple-silicon GPU)

Stable-Baselines3's `device="auto"` only ever checks CUDA and silently falls
back to CPU on a Mac. `tccpl_learner.resolve_device()` therefore prefers
**cuda → mps (Apple GPU) → cpu**, and every learner reads `CONFIG["device"]`
(override with `TCCPL_DEVICE=cpu|mps|cuda`). Measured on a MacBook Pro M5 Pro,
per TC-CPL gradient step (B = 256, nets + transfers):

| Scenario | cpu | mps | speed-up |
|---|---|---|---|
| PublicPST (N=20) | 18.3 ms | 10.1 ms | 1.8× |
| cityNL (N=600) | 557.6 ms | 128.1 ms | **4.4×** |

The bf16 encoder autocast remains CUDA-only; mps runs fp32.

## Constraint tightening (requirements vs. training thresholds)

Problem 1's **requirements** — the quantities §7 evaluates and the paper reports —
are `target_overload = 0` kWh and `target_sat = 0.95`. The learner is trained
against strictly **tighter surrogates** (a standard back-off): the dual-priced
overload counts loading above `(1 − ov_margin) ×` the DR-aware transformer limit
(EV-controllable part; `ov_margin = 0.05`), and the PI dual controller targets
`train_sat_floor = 0.98`. Both are overridable per run with `TCCPL_OV_MARGIN`
and `TCCPL_TRAIN_SAT_FLOOR` (see `runall.sh`).

Why tighten the *limit* and not the *threshold*: a negative energy threshold
(e.g. "overload ≤ −3 kWh") is infeasible because overload energy is
non-negative, so the integral term would ratchet λ_ov to λ_max regardless of
the policy and the Lagrangian analysis would no longer hold. Tightening the
limit gives the same pressure toward zero while keeping the constraint
satisfiable (zero charging always satisfies it), so λ can settle once loading
stays under the tightened limit — at which point true overload is exactly zero.
`train_target_overload < 0` is still accepted as an experimental pressure mode
and prints a warning.

## Multiplier units (read before re-tuning)

The paper prices the normalized cost c_ov = kWh/E_ref. The PI controller adapts
λ_ov in interpretable **kWh-price units** (`lambda_init_ov`, `lambda_ki`, … in
CONFIG), and `TCCPLCosts` converts once by the exact factor
E_ref/P_ref = T·Δt (24 on cityNL, 28 on PublicPST). Fixed positive rescaling
changes neither the feasible set nor the optimizer (paper Sec. III-B); it keeps
the λ-evolution figure and the gains on the same scale the earlier experiments
were tuned in. The two auxiliary-signal coefficients (`aux_ov_coef`,
`aux_sat_coef`) use the same convention and are annealed to zero over the first
80 % of training — identically for TC-CPL and its ablation.

## Training-speed notes

- TF32 matmuls + bf16 autocast inside the M3 encoders (Ampere+ GPUs); PER
  priorities are cached in exponentiated form and refreshed from the TD errors
  the critic update computes anyway — no extra forward passes.
- DDPG buffer = min(1e6, budget), i.e. the paper's 1e6 at the 1M-step protocol
  (~18 GB float32 at cityNL's observation size — a cluster-node quantity; set
  `TCCPL_DDPG_BUFFER=300000` on a laptop for a sliding window instead).

## Cluster protocol (1,000,000 steps × 5 seeds)

`slurm_sweep.sh` is a SLURM array template: 50 tasks = 2 scenarios × 5 seeds ×
5 algorithms, each a `train_one.py` process on its own CPU/GPU allocation.
Edit the `#SBATCH` header for the target system (partition, GPU, RAM — DDPG at
cityNL needs ~24 GB, the others ~8 GB), activate the environment in the marked
line, then

```bash
sbatch slurm_sweep.sh                 # everything
sbatch --array=0-24 slurm_sweep.sh    # cityNL only (tasks 0–24)
```

Finished jobs (runmeta at the current budget) exit immediately, so a failed
array can simply be resubmitted. Afterwards copy `models/`, `logs/` and
`results/` back and run notebook §7 once per scenario. Without SLURM,
`python run_sweep.py --jobs N` gives the same 50 jobs with bounded concurrency.
- The remaining wall-clock cost is structural: one gradient step per
  environment transition (protocol parity) and serial `DummyVecEnv` stepping.
  `SubprocVecEnv` is not used because M1's dual update reaches every worker by
  mutating one shared reward object, which requires in-process envs;
  parallelism across *runs* comes from `run_sweep.py` instead.
